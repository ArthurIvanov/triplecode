# Работа AI-агентов в TripleCode

На старте задачи выбери ведущую роль по требуемому результату. Укажи её, критерии приёмки и путь к итоговому артефакту в задаче или PR. Одна сессия может последовательно менять роли. Для критичных изменений проверку проводит отдельная AI-сессия с доступом к исходной задаче, diff и результатам тестов.

| Роль | Когда брать | Решения и результат |
| --- | --- | --- |
| Продакт-менеджер | Цель, приоритет, выбор границ релиза | Определяет сценарий, сегмент и критерии успеха. Ведёт план релизов и фиксирует продуктовые решения |
| Продуктовый исследователь | Неясна потребность или конкурентная практика | Формирует вопросы, исследует первичные источники и рабочие сценарии, отделяет наблюдения от гипотез |
| Продуктовый дизайнер | Интерфейс, миграция, управление агентом | Проектирует сценарии, прототипы, состояния ошибок, клавиатурную навигацию и доступность. Готовит критерии принятия дизайна |
| Архитектор дизайн-системы | Общие компоненты, токены, синхронизация с Figma | Привязывает реализацию к узлам Figma, согласует состояния и токены между галереей и приложением, проверяет компонент в обоих местах |
| Продуктовый аналитик | Метрика, эксперимент, качество AI | Определяет события, знаменатели, выборки и условия остановки. Выпускает отчёт с данными и ограничениями |
| Архитектор | Границы модулей, зависимости, upstream | Сравнивает варианты, фиксирует решение и условия пересмотра, задаёт контракты и план миграции |
| Инженер IDE | Workbench, расширения, профили, desktop | Реализует минимальное сквозное изменение и проверяет совместимость с upstream и существующими профилями |
| Инженер AI | Контекст, модели, сессии, инструменты | Реализует поток ответов, отмену, ограничения инструментов и воспроизводимые оценки качества |
| QA-инженер | Приёмка, регрессии, совместимость | Гоняет сценарии на целевых ОС, прикладывает логи и сообщает о непроверенных случаях |
| Инженер безопасности | Доступ к коду, команды, расширения, облако | Проверяет границы доверия, правила доступа к данным и обработку секретов. Блокирует релиз при критичных нарушениях |
| Инженер релизов | CI, упаковка, обновления, эксплуатация | Собирает воспроизводимые артефакты, проверяет подпись, обновление, откат релиза и эксплуатационные метрики |

## Обязательные правила для любой модели

- Перед правками прочитай этот файл, инструкции в затронутых каталогах и [правила разработки IDE](docs/engineering.md). Проверь текущую ветку, незакоммиченные изменения и критерии приёмки.
- Веди задачу на отдельной ветке. Для одновременной работы используй отдельный Git worktree. Согласуй владельца общих файлов и порядок слияния через задачу или PR.
- Сохраняй чужие изменения. При пересечении с активной работой зафиксируй конфликт и согласуй интеграцию до правок общего файла.
- Фиксируй решения и проверяемое состояние в репозитории, задаче или PR. Ссылка на приватную сессию может быть дополнением к этому контексту.
- Перед передачей работы приложи команды проверок, результаты и следующее действие. Явно отметь проверки, которые пропущены или заблокированы.

## Git flow

- После каждого запроса фиксируй результат: `git add` → `git commit` → `git push` в текущую рабочую ветку. Незакоммиченная работа считается потерянной.
- Перед началом крупной доработки и после её завершения синхронизируйся с облаком: `git fetch` → `git pull` (или merge `origin/<ветка>`). При расхождении сначала влей удалённые изменения, разреши конфликты, проверь сборку — и только потом продолжай.
- Параллельные сессии часто переключают ветку и оставляют незакоммиченные правки. Перед коммитом проверяй `git status` и `git branch --show-current`: не захватывай чужие изменения в свой коммит; при пересечении по файлам согласуй порядок через задачу или PR.
- Не пушь в `master` напрямую и не делай force-push без явной просьбы пользователя.

## Правила мержа

- `master` сейчас содержит единственный несвязанный коммит `first commit` и не является интеграционной базой. Рабочие ветки (`codex/*`, `devin/*`) ответвляются от общей линии истории — сейчас это `codex/agent-timeline`.
- Перед открытием PR проверь общую историю: `git merge-base HEAD origin/<base>` должен вернуть коммит. Если базы нет — остановись и согласуй интеграционную ветку, не создавай PR «в никуда».
- Интеграционная ветка одна и называется в задаче или PR. Пока отдельная не выделена, базой служит ветка с общей историей, указанная в PR.
- Один PR доводит один сценарий. Зависимые PR перечисляют порядок применения; тот, кто мержит вторым, сначала вливает первый и перепроверяет сборку.
- `extensions/triplecode-mvp/extension.js`, `provider.js`, `package.json` и `docs/product-plan.md` — горячие файлы: при параллельной работе назначай владельца интеграции и согласуй порядок до правок.
- Мержит PR автор после прохождения проверок из раздела «Передача работы», либо назначенный интегратор. После мержа ветка удаляется, worktree убирается (`git worktree remove`).
- Конфликт при мерже разрешается в пользу обеих изменений, если они не противоречат; при противоречии фиксируется решение в PR, а не молча выбирается сторона.

## Дизайн-система

Для задач по UI, компонентам, токенам и Figma применяй [правила дизайн-системы TripleCode](design%20system%20rules/README.md).

## Передача работы

1. Продакт задаёт пользовательский результат. Исследователь и аналитик проверяют предпосылки, дизайнер определяет сценарий, архитектор фиксирует существенные технические решения.
2. Ведущий инженер доводит задачу до работающего результата. В PR остаются ссылка на задачу, затронутые сценарии, команды проверки и фактический результат.
3. QA проверяет критерии приёмки. Для особых областей добавляется ревью профильной роли. При изменении релизных границ продакт обновляет дорожную карту.
4. Агенты выполняют исследование, дизайн, реализацию, тестирование, документацию и подготовку релиза. Руководитель продукта задаёт стратегию и принимает решения о публичном релизе, обработке пользовательских данных и расходах.

Фиксируй гипотезы и непроверенные результаты явно. Обновляй [карту паритета](docs/product-plan.md) при изменении объёма релиза и [архитектурное решение](docs/architecture.md) при изменении технического курса.
