# Исследование конкурентов и архитектура TripleCode

Срез публичных источников на 21 ноября 2026 года. Описание конкурентов основано на исходниках и документации производителей. Производительность, долю совместимых расширений и качество AI предстоит измерить на одинаковых задачах.

## VS Code

- Code — OSS написан на TypeScript. `base` содержит общие примитивы, `platform` — сервисы, `editor` — Monaco, `workbench` — представления и интеграции, `code` — desktop и CLI, `server` — серверную точку входа. В текущих правилах исходников также выделен слой `sessions` для окна сессий. Разделение по runtime ограничивает доступ к Node и Electron из UI. [Правила организации исходников](https://github.com/microsoft/vscode/blob/main/.github/instructions/source-code-organization.instructions.md)
- Workbench реализует оболочку, палитру, панели и API расширений. Monaco покрывает редактор, а расширения исполняются через Extension Host. Новый shell поверх одного Monaco потребовал бы заново реализовать эти контракты и заново проверить совместимость. [Source Code Organization](https://github.com/microsoft/vscode/wiki/Source-Code-Organization)
- Microsoft ведёт публичный репозиторий и публикует планы итераций. Руководство описывает локальную сборку, запуск из исходников и тестирование. Для TripleCode это исходная точка CI и сопровождения форка. [How to Contribute](https://github.com/microsoft/vscode/wiki/How-to-Contribute)
- Репозиторий доступен по MIT. Дистрибутив Microsoft добавляет собственные материалы, Marketplace и часть интеграций Remote Development. Доступность исходников, право распространения расширения и его фактическая работоспособность проверяются отдельно. [Лицензия репозитория](https://github.com/microsoft/vscode/blob/main/LICENSE.txt) · [FAQ Microsoft](https://code.visualstudio.com/docs/supporting/faq)
- Сильные стороны для наших пользователей — API расширений, отладка, терминал, Git, профили и привычные команды. VS Code также предлагает интерактивные, фоновые и облачные сессии. Эти возможности нужно учитывать при оценке паритета. [Профили](https://code.visualstudio.com/docs/configure/profiles) · [Агенты](https://code.visualstudio.com/features/agents) · [Agent harnesses](https://code.visualstudio.com/docs/agents/run/agent-harnesses)

## Cursor

- Cursor подтверждает происхождение от Code — OSS и описывает регулярные слияния с upstream и отдельный перенос критичных исправлений. Полезный вывод для TripleCode — сделать обновление upstream частью CI с самого начала и измерять стоимость каждого изменения ядра. [Cursor Security](https://www.cursor.com/en/security)
- Миграция построена вокруг переноса расширений, тем, настроек и клавиш, включая импорт профиля. В рабочем процессе Cursor различает Ask, Plan, Agent и Debug и показывает изменения в diff. Сильная сторона — короткий переход от обычного редактирования к AI-задаче. [Миграция](https://docs.cursor.com/get-started/migrate-from-vs-code) · [Agent mode](https://prod.cursor.com/help/ai-features/agent)
- Текущая документация описывает Instant Grep с локальным поисковым индексом. Открытый агентом фрагмент при этом может попасть в запрос модели. Для MVP отсюда следует раздельно проектировать локальный поиск и правила отправки контекста. [Cursor Search](https://cursor.com/docs/agent/tools/search)
- Облачные задачи имеют подготовку среды, ветку для PR и настройки команды. Отчёт Composer 2 описывает обучение и инфраструктуру AnyRun для исследовательских запусков, но оставляет детали производственной архитектуры неполными. Точные внутренние контракты, затраты и текущий production-стек Cursor публично не установлены. [Cloud Agents](https://prod.cursor.com/docs/cloud-agent/settings) · [Composer 2 Technical Report](https://cursor.com/resources/Composer2.pdf)

## Devin

Сильная сторона — асинхронная работа от постановки задачи и предварительного плана до просмотра в IDE и PR. Cognition описывает подготовленные окружения, переиспользуемые знания о репозитории и делегирование частей задачи отдельным сессиям. TripleCode может перенять плавную передачу работы между человеком и сессией. Для MVP достаточно одной возобновляемой интерактивной сессии с результатами проверок. [Devin Docs](https://docs.devin.ai/get-started/devin-intro) · [Devin 2.0](https://cognition.com/blog/devin-2) · [Manage Devins](https://cognition.com/blog/devin-can-now-manage-devins)

## Как Cursor меняет оболочку

Cursor подтверждает форк Code — OSS. Есть и прямое свидетельство о стоимости поддержки UI: разработчик Cursor объяснил переход в версии 2.6 тем, что классическая и новая агентская компоновки имели отдельные реализации, которые команда больше не могла развивать параллельно. В Cursor 3 появилось отдельное Agents Window. Оно может быть открыто одновременно с IDE и получило собственное деление на плитки с восстановлением состояния. Публичные материалы описывают эти решения на уровне продукта и сопровождения. Граница между их собственным кодом и унаследованным Workbench в каждом окне остаётся неизвестной. [Cursor Security](https://www.cursor.com/en/security) · [Ответ разработчика о версии 2.6](https://forum.cursor.com/t/old-editor-ui-broke-up-after-update/154545/6) · [Cursor 3.0](https://cursor.com/changelog/3-0) · [Cursor 3.1](https://cursor.com/changelog/3-1)

### Что именно можно перемещать в Code — OSS

| Изменение | Уровень реализации |
| --- | --- |
| Поменять сторону Sidebar или положение Panel | Штатные настройки и команды Workbench |
| Перенести отдельное представление или его контейнер между доступными областями | Механизм views и контейнеров. В исходниках местоположение сохраняет `ViewDescriptorService`. Допустимость переноса зависит от представления |
| Вложить терминал под редактором, оставив соседний чат на всю высоту, если штатные варианты не дают нужную геометрию | Изменить топологию сетки Workbench и согласовать фокус, ограничения размеров, сворачивание, команды и восстановление состояния |
| Сделать окно AI-задач с другим набором частей | Собственная композиция на уровне отдельного окна. Публичный пример есть в слое `vs/sessions` самого Code — OSS. Его наличие проверяем на выбранном теге |

Workbench управляет частями через `SerializableGrid` и регистрирует Editor, Sidebar, Auxiliary Bar, Panel и другие части. CSS может менять их оформление. При перестановке части меняется её место в сетке и связанные контракты. Extension Host тоже связан с клиентской половиной API в Workbench. При замене оболочки его запуск сам по себе не обеспечит работу представлений, команд и webview расширений. [Custom Layout](https://code.visualstudio.com/docs/configure/custom-layout) · [Contribution Points](https://code.visualstudio.com/api/references/contribution-points#contributesviewscontainers) · [Workbench layout](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/browser/layout.ts) · [ViewDescriptorService](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/services/views/browser/viewDescriptorService.ts) · [Sessions layout](https://github.com/microsoft/vscode/blob/main/src/vs/sessions/LAYOUT.md)

## Решение для первого прототипа

| Вариант | Что даёт | Цена |
| --- | --- | --- |
| Тонкий форк Code — OSS | Редактор, Workbench, Extension Host, CLI и возможность встроить AI в нужное место | Регулярные слияния, упаковка, отдельные сервисы дистрибутива |
| Расширение для VS Code | Быстрая проверка агентских сценариев через публичный API | Ограниченный контроль собственных экранов, миграции и дистрибутива |
| Новый shell с Monaco | Свобода UI и runtime | Повторная реализация профилей, Extension Host, отладки, терминала и совместимости |

Выбираем Code — OSS на TypeScript и Electron как базу эксперимента. Глубина форка зависит от проверки компоновки. ОС первого прототипа — macOS arm64, исходя из текущей среды проекта. Windows x64 и Linux x64 входят в матрицу публичной беты. Версию upstream выбираем при сборке из актуального стабильного тега, фиксируем SHA и сохраняем сведения о происхождении и уведомления об авторских правах.

- **Workbench.** Используем штатные сервисы профилей, редактора, команд и diff. TripleCode добавляет представление AI, миграцию и настройки провайдера как отдельные contributions. Интерфейс сохраняет привычное расположение Explorer, редактора, AI-панели и терминала и использует собственный визуальный стиль.
- **Миграция.** Основной путь читает локальную конфигурацию VS Code после явного запуска импорта. Для другого устройства или отсутствующей локальной установки поддерживаем экспортированный профиль через Profiles. При выборе категорий или конфликте показываем настройки, клавиши, сниппеты, задачи, темы и расширения в предпросмотре. Настройки, запускающие процессы, и задачи требуют явного выбора. Применяем импорт в отдельный профиль, оставляем исходные файлы доступными для повторного импорта и проверяем повторный запуск, частичный сбой и откат. Расширения разрешаем по ID и проверяем версию, зависимости, платформу и лицензию. Кандидат на каталог — Open VSX. VSIX поддерживаем при наличии права на использование. Учётные данные и секреты заново привязываются пользователем. Решение по ADR 0003: использование штатного Profiles API для MVP. [Профили VS Code](https://code.visualstudio.com/docs/configure/profiles) · [Open VSX](https://github.com/eclipse-openvsx/openvsx)
- **AI runtime.** Workbench передаёт идентификатор задачи и выбранный контекст через типизированный IPC в отдельный процесс. Адаптер модели стримит ответ и события. Для первого прототипа достаточно одного провайдера, локального текстового поиска и явных ссылок на файл или выделение. Запросы допускают отмену. Ключ хранится в защищённом хранилище ОС. Отдельно измеряем время получения контекста и модели.
- **Исполнение.** Runtime предлагает патч и команды проверки. Исполнитель проверяет область доступа и решение пользователя. Git worktree изолирует рабочие изменения от основной копии, а отдельная песочница ограничивает процессы, файловую систему и сеть. При отсутствии подходящей песочницы оставляем агенту анализ и проверяемый патч. При применении сверяем базовое состояние каждого файла. Откат сохраняет последующие изменения пользователя и показывает конфликт, если автоматическое восстановление неоднозначно.
- **Сессии и данные.** Храним локально переходы состояний, ссылки на патчи, решения пользователя, команды и результаты проверок. После перезапуска восстанавливаем состояние интерфейса и последний подтверждённый шаг. Повтор запроса на запись или выполнение команды проверяем по ID операции. Содержимое исходников и секреты исключаем из продуктовой телеметрии.
- **Сопровождение форка.** Сначала CI собирает чистый upstream, затем TripleCode на том же SHA. Смоук включает запуск, открытие проекта, терминал, Git, установку разрешённого расширения и загрузку профиля. Для каждого стабильного upstream-релиза оцениваем merge и результаты CI, критичные исправления рассматриваем вне очереди. Два последовательных обновления с ручным вмешательством в ядро требуют пересмотра границы интеграции.

Первый технический результат — локально запускаемый TripleCode с одним установленным расширением из разрешённого источника, одним импортируемым профилем и AI-панелью, которая показывает патч. Если сборка и совместимость проходят, продолжаем как форк. Если интеграция блокируется границами API или стоимостью merge, возвращаемся к сравнению архитектур на фактических результатах.

## Electron, Rust и производительность

Для прототипа сохраняем Electron, TypeScript и существующий Node.js Extension Host. Electron поставляет Chromium и Node.js и использует несколько процессов. Это влияет на размер поставки и базовое потребление ресурсов. Отзывчивость IDE зависит также от работы renderer, активации расширений, языковых серверов и фоновых задач. Rust в отдельном процессе может ускорить конкретную вычислительную операцию, но сам по себе не снизит базовую стоимость Chromium или задержку ответа облачной модели. [Модель процессов Electron](https://www.electronjs.org/docs/latest/tutorial/process-model) · [Рекомендации Electron по профилированию](https://www.electronjs.org/docs/latest/tutorial/performance)

| Вариант | Что проверить для TripleCode |
| --- | --- |
| Electron + штатный поиск | Начальная реализация. VS Code уже вызывает написанный на Rust ripgrep отдельным бинарником. Для AI-контекста сначала проверяем переиспользование штатного поиска |
| Electron + отдельный процесс на Rust | Кандидат для инкрементальной индексации символов или другой локальной обработки репозитория, если замеры покажут узкое место. Сравниваем с отдельным процессом на Node.js и учитываем запуск, IPC, сериализацию и весь процессный бюджет |
| Tauri + системный WebView | Требует адаптации desktop-интеграций Code — OSS, IPC и webview расширений, а также отдельного Node.js runtime для совместимых desktop-расширений. Проверяем поведение на WKWebView, WebView2 и WebKitGTK. Возможный выигрыш в размере поставки оцениваем отдельно от памяти и отзывчивости |
| Нативный UI на Rust | Даёт контроль над отрисовкой и оболочкой. Совместимость с VS Code потребует воспроизвести клиентские контракты расширений. Zed показывает жизнеспособность нативной IDE и использует собственный формат расширений |

[Поиск VS Code](https://github.com/microsoft/vscode/wiki/Search-Issues) · [Архитектура Tauri](https://v2.tauri.app/concept/architecture/) · [Расширения Zed](https://zed.dev/docs/extensions/developing-extensions)

Граница для подключения Rust — API фоновой операции с потоковой выдачей результатов и отменой. При необходимости подключаем отдельный исполняемый файл из Node.js и версионируем протокол. Сопоставляем время запуска, данные на IPC, пиковую память, устойчивость к завершению процесса и стоимость упаковки для macOS, Windows и Linux. Файловые и сетевые ограничения задаёт среда запуска, независимо от языка.

В этапе 0 сравниваем чистый Code — OSS и TripleCode на одном SHA, одной машине, одинаковых репозиториях и наборах расширений. Меряем холодный и тёплый запуск до ввода, память и CPU по дереву процессов в простое, p95 времени поиска и p95 задержки ввода во время фоновой работы. Первый ответ AI разбиваем на локальную подготовку контекста и сетевой ответ модели. Rust-прототип нужен, если профилирование локализует воспроизводимый дефицит в вычислениях на клиенте. Оставляем его, если заметно улучшается пользовательский сценарий с учётом IPC и ресурсоёмкости. Замеры пока не выполнены. [Профилирование VS Code](https://github.com/microsoft/vscode/wiki/Performance-Issues)

## AI-автодополнение и прогноз следующей правки

**Cursor Tab.** При наборе или перемещении курсора модель предсказывает следующее действие. Документация называет контекст вокруг курсора, недавние правки и ошибки линтера. Интерфейс показывает серый текст, многострочные изменения и переход к следующей правке в том же или другом файле. Cursor публиковал описания специализированной модели Fusion и последующего обучения Tab на пользовательской обратной связи. Эти публикации описывают отдельные поколения модели. Текущая серверная реализация, правила отбора контекста и пороги показа полностью не раскрыты. [Cursor Tab](https://cursor.com/help/ai-features/tab) · [Fusion](https://cursor.com/en-US/blog/tab-update) · [Обучение Tab](https://cursor.com/blog/tab-rl)

**VS Code и GitHub Copilot.** Code — OSS содержит редакторский механизм inline-подсказок. Публичный API `vscode.languages.registerInlineCompletionItemProvider` регистрирует провайдер, которому редактор передаёт документ, позицию, контекст вызова и токен отмены. Copilot добавляет вставку у курсора (ghost text) и Next Edit Suggestions (NES), которые предсказывают место и содержание связанной правки. В открытом исходнике провайдера NES видны обработка отмены, кандидаты от модели и диагностики, переход к позиции и отдельная обработка правок другого документа. Этот исходник описывает клиентскую интеграцию. Для TripleCode потребуется собственный адаптер модели. Возможности NES, выходящие за рамки стабильного API, сверяем с декларациями выбранного upstream-тега. [API VS Code](https://code.visualstudio.com/api/references/vscode-api#languages.registerInlineCompletionItemProvider) · [Подсказки VS Code](https://github.com/microsoft/vscode-docs/blob/main/docs/editing/ai-powered-suggestions.md) · [Провайдер NES](https://github.com/microsoft/vscode-copilot-chat/blob/main/src/extension/inlineEdits/vscode-node/inlineCompletionProvider.ts)

**TripleCode.** Первая версия — встроенное расширение на TypeScript через стабильный API. Используем штатный рендеринг и команды редактора. Отдельный адаптер запрашивает короткое дополнение по коду до и после курсора. Поддержка fill-in-the-middle у модели — критерий сравнения провайдеров. Ограничиваем размер контекста, проверяем настройки языка и проекта до сетевого запроса и отбрасываем ответ при смене документа, версии или позиции. При медленном ответе, отмене или недоступности провайдера набор продолжается. Проверяем подсказки совместно с IntelliSense и переназначенными клавишами.

Для беты меряем p50/p95 времени от триггера до видимой подсказки, долю принятых среди показанных, долю быстрых отмен после принятия, объём запросов и задержку ввода под нагрузкой. На одинаковых сценариях проверяем устаревшие ответы, переключение файлов, офлайн-режим и запрет передачи контекста из исключённых файлов. Следующее расширение функции — локальные замены, затем переходы по файлу и межфайловые предложения. Для межфайловой правки проверяем версию целевого документа и показываем изменение до применения.

## Дистрибутив macOS MVP

Первый самостоятельный бандл для Apple Silicon собирается из закреплённого дистрибутива VSCodium на базе Code — OSS. В него встроено расширение TripleCode MVP. Границы этого решения и результаты приёмки описаны в [ADR 0001](adr/0001-macos-mvp-distribution.md).

## Сервисы дистрибутива

Встроенные AI-функции используют аккаунт TripleCode и серверную проверку прав. Локальные функции IDE доступны без аккаунта. Конфигурацию продукта и места входа в сторонние сервисы проверяем при каждом обновлении upstream. [Аккаунт, подписка и аналитика](accounts.md).
