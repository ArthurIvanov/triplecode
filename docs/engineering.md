# Правила разработки TripleCode IDE

## Источники контекста

| Где | Что хранится |
| --- | --- |
| `AGENTS.md` | Общие инструкции, роли и правила начала и окончания работы |
| Вложенный `AGENTS.md` | Инструкции для конкретного каталога, если у него появятся особые команды или ограничения |
| `docs/product-plan.md` | Сценарии, паритет, границы релизов и критерии выхода |
| `docs/architecture.md` | Текущая архитектура, гипотезы и условия их проверки |
| `docs/adr/` | Принятые архитектурные решения, создаётся при первом ADR |
| Задача и PR | Критерии приёмки, текущее состояние, изменения и доказательства проверок |

`AGENTS.md` — общий вход для всех агентов. Если инструменту требуется собственный файл инструкций, укажи в нём путь к `AGENTS.md` и короткие инструкции запуска для этого инструмента. Общие правила редактируются в одном месте. Контекст задачи должен быть доступен следующему агенту с доступом к репозиторию и трекеру.

## Параллельная работа и Git

- Заводи ветку от согласованного базового коммита. Для продуктов, автоматически задающих префикс, сохраняй их префикс и добавляй короткое имя задачи. При параллельных задачах у каждой ветки свой worktree и один агент, который интегрирует изменения.
- Перед началом запиши в задаче базовый SHA, область работы и зависимости. Если несколько задач меняют один контракт, реестр, lockfile или точку входа, назначь владельца интеграции и согласуй порядок PR.
- Один PR должен доводить до приёмки один сценарий или самостоятельный шаг. Укажи порядок применения зависимых PR. Перед ревью сверь diff с базой, а после разрешения конфликта повтори затронутые проверки.
- Для долгой задачи оставляй передаваемый коммит на рабочей ветке, если это разрешено. Если изменения ещё в worktree, укажи его путь и перечень незакоммиченных файлов в отчёте о передаче.

## Работа с исходниками

- После подключения форка сохраняй структуру upstream. Новые возможности добавляй через существующие контракты расширений и Workbench. Изменения общих модулей, layout, Extension Host и упаковки делай локальными и фиксируй причину в PR.
- Обновление upstream веди отдельно от продуктовой задачи. Запиши исходный и целевой SHA, список конфликтов и способ их разрешения. Проверь запуск, редактор, расширения, профили и собственные точки интеграции. Для desktop-специфичных изменений укажи проверенные ОС.
- Следуй соглашениям затронутого каталога о названиях, слоях, форматировании и тестах. Обновляй lockfile вместе с зависимостью. Генерируемые файлы изменяй через их источник и используемый генератор.
- Для изменений, затрагивающих интерфейс, контракты, сохранённые данные или поведение команд, проверь реальную точку входа и совместимость со старыми профилями или клиентами, где это применимо.
- Временные выводы, логи сборки и результаты экспериментов прикладывай к задаче или PR. Храни в репозитории воспроизводимые проверки и долговременные решения. Используй тестовые данные без токенов, пользовательского кода и персональных данных.

## Архитектурные решения

Для решений, меняющих формат данных, внешние контракты, границы подсистем или глубину форка, создай ADR вида `docs/adr/0001-short-topic.md`. Запиши статус, дату, контекст, рассмотренные варианты, решение, последствия и условия пересмотра. При замене принятого решения добавь ссылку на новый ADR в старом. Обнови `docs/architecture.md`, чтобы она отражала текущее устройство продукта.

## Проверка и передача

Проверяй критерии приёмки через штатный путь пользователя. Запускай проверки, соответствующие изменению. Для дефекта, который существующие тесты пропускают, добавь регрессионную проверку. Изменения миграции, обновлений, исполнения агентских действий и совместимости расширений требуют независимой проверки другой AI-сессией по исходной задаче, diff и результатам тестов.

В задаче или PR оставь короткую запись по этому формату:

- Задача, ведущая роль и критерии приёмки
- Ветка, базовый SHA и проверенный коммит или путь к рабочему дереву
- Что сделано и какие файлы или контракты затронуты
- Команды, ОС или среда и фактические результаты
- Что осталось, что блокирует работу и какое действие выполнить следующим

При смене модели продолжай с этой записи и сверяй её с Git. Для завершённой задачи результаты проверок должны подтверждать критерии приёмки. Если обязательная проверка ещё впереди, сохрани её в статусе задачи и записи о передаче.
