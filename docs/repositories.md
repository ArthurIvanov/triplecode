# Структура репозиториев TripleCode

Начинаем с двух репозиториев. Текущий `triplecode` становится репозиторием IDE и хранит общие продуктовые документы. Новый `triplecode-web` объединяет публичный сайт, кабинет и серверную часть. Бэкенд можно развёртывать отдельно от сайта из того же репозитория.

| Репозиторий | Что в нём | Что выпускает |
| --- | --- | --- |
| `triplecode` | Форк Code — OSS с upstream-структурой, встроенные AI-расширения, desktop-интеграция, смоук-тесты, упаковка и обновления | Подписанные установщики и метаданные релиза |
| `triplecode-web` | Публичные страницы, скачивание, регистрация и вход, кабинет, серверные API, миграции базы и обработка платежей | Веб-приложение и серверные сервисы |

Форк ведём с сохранением истории upstream и структуры его дерева, чтобы регулярные слияния затрагивали только IDE. Веб-часть выпускается независимо. Изменение лендинга, кабинета или биллинга может попасть в продакшен между релизами IDE. Общие изменения связываем одной продуктовой задачей и PR в обоих репозиториях.

## Начальная структура веб-проекта

```text
triplecode-web/
  AGENTS.md
  apps/
    web/          # продуктовые страницы, скачивание, вход и кабинет
    api/          # аккаунты, права, биллинг, AI и учёт использования
  packages/
    contracts/    # версия схемы внешнего API
```

Публичные страницы и кабинет начинаем как одно веб-приложение с отдельными маршрутами. Публичные страницы можно кэшировать, а доступ к кабинету и данным проверяет сервер. Для API достаточно одного приложения с отдельными модулями аккаунтов, прав, биллинга и аналитики. Дробление по сервисам рассматриваем, когда появляются разные требования к масштабированию или выпуску.

## Связь между репозиториями

- **API.** Каноническая схема API хранится в `triplecode-web`. IDE использует версионированный клиент по этой схеме. Сервер проверяет права на AI и лимиты. При изменении контракта сначала выпускаем обратно совместимый API, затем IDE, поскольку установленные клиенты обновляются постепенно. В CI веб-проекта проверяем совместимость с поддерживаемыми версиями клиента.
- **Сборки.** CI IDE публикует подписанные установщики в хранилище артефактов, проверяет доступность, затем обновляет манифест релиза с версией, каналом, ОС, архитектурой, ссылкой и контрольной суммой. Страница загрузок читает манифест. Канал обновлений IDE использует метаданные той же публикации. Откат возвращает указатель стабильного канала к проверенной версии.
- **Вход.** IDE открывает браузер для входа в TripleCode и получает desktop-сессию по контракту сервера. Веб-кабинет обслуживает покупку и управление подпиской. Подробности описаны в [плане аккаунта](accounts.md).
- **Релизы и секреты.** Подпись desktop-сборок и доступ к публикации настроены в CI IDE. Серверные ключи, платёжные уведомления и доступ к базе принадлежат среде API. У сайта достаточно чтения публичного манифеста.

Единый репозиторий упростил бы атомарные правки клиента и сервера, но добавил бы веб-проект в дерево сопровождаемого форка. Три репозитория с отдельным бэкендом дали бы ещё одну границу релиза ценой координации изменений аккаунта, кабинета и API. На текущем этапе две границы соответствуют двум основным циклам работы, IDE и веб-платформе.

Текущий этап — решение о структуре. Новый репозиторий, CI и хранилище сборок ещё не созданы.
