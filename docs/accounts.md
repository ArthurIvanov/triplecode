# Аккаунт, подписка и аналитика TripleCode

## Самостоятельный дистрибутив

TripleCode использует собственный аккаунт для встроенных AI-функций, личного кабинета и подписки. Редактирование, локальный импорт профиля, терминал и локальный Git доступны без регистрации. Сторонние расширения и явно подключённые интеграции могут запрашивать отдельный вход для своих функций. Например, подключение GitHub для PR не влияет на регистрацию или подписку TripleCode.

На фиксированном SHA Code — OSS проверяем конфигурацию продукта, состав встроенных расширений и точки входа в AI. Убираем предложение установить или подключить Copilot и вход Microsoft/GitHub для обслуживания TripleCode. Импорт пропускает сессии и токены, а настройки сторонних сервисов отображает в отчёте. Собственное обновление, каталог расширений и будущая синхронизация получают отдельную конфигурацию. На чистом профиле проверяем первый запуск, меню аккаунтов, кнопку AI, inline-подсказки, импорт и сетевые обращения в этих сценариях. [Конфигурация upstream](https://github.com/microsoft/vscode/blob/main/product.json) · [Settings Sync VS Code](https://code.visualstudio.com/docs/configure/settings-sync)

## Что берём за ориентир у Cursor

Web-кабинет для управления планом и расходами, а для команд — показатели активности, AI-правок, предложений Tab и использования моделей. Cursor описывает командные роли и ограничения видимости. Текущие платёжные маршруты Cursor зависят от плана. Для TripleCode выбираем собственный кабинет с одним понятным маршрутом покупки. [Billing and payments](https://cursor.com/help/account-and-billing/billing) · [Usage Analytics](https://cursor.com/docs/account/teams/analytics)

## Предлагаемый пользовательский сценарий

1. Пользователь открывает IDE и начинает работу с локальным проектом. Для встроенного AI выбирает «Войти в TripleCode» и регистрируется по email в браузере.
2. Desktop получает сессию через OAuth Authorization Code с PKCE. Токен обновления хранится в защищённом хранилище ОС. Пользователь видит профиль, план и остаток лимита в IDE и может завершить сессию устройства из кабинета. [OAuth для нативных приложений](https://www.rfc-editor.org/rfc/rfc8252)
3. Кнопка покупка открывает hosted checkout. Кабинет показывает состояние платежа и план, позволяет открыть счета, обновить способ оплаты или отменить продление. Для первого платного релиза предлагаем индивидуальную подписку, привязанную к аккаунту. Тариф, цены, страны продаж и платёжный провайдер остаются открытыми решениями.
4. Право на AI-функции и квоты проверяются сервером. После подтверждённого платежа сервер обновляет права, desktop обновляет их при возврате из браузера. Если подтверждение задерживается, интерфейс показывает ожидающий платёж. При истечении подписки локальная IDE доступна, а AI работает в пределах действующего плана.

## Данные и проверка

- **Аккаунт и биллинг.** Сервер хранит ID пользователя, связь с ID клиента у платёжного провайдера, план, срок действия и права на функции. Карточные данные обрабатывает hosted checkout. Платёжные уведомления проверяются по подписи и обрабатываются идемпотентно. При дубликатах и событиях вне очереди сверяем актуальное состояние подписки с провайдером. Приёмка охватывает покупку, отклонённую оплату, отмену, истечение, возврат и повторную доставку.
- **Расход и лимиты.** Сервер учитывает тарифицируемые операции по уникальному ID, фиксирует модель, объём и период. Кабинет показывает использованный и доступный объём и дату обновления лимита. Повтор запроса не приводит к двойному списанию. Показатели оплаты сверяются с платёжным провайдером.
- **Личная аналитика.** Кабинет показывает по периоду число AI-запросов по функциям, принятые правки агента и для Tab отдельно показанные и принятые подсказки. Доля принятия считается от показанных подсказок. Принятие измеряет взаимодействие с функцией. Экономию времени оцениваем отдельно в пилоте.
- **Командная аналитика.** Добавляем агрегаты по организации, активных пользователей AI, распределение по функции и моделям и командный расход. Сервер проверяет членство и роль на каждом запросе. Участник видит личные данные, администратор видит командные агрегаты в пределах своей организации. Приёмка проверяет изоляцию между организациями и доступ после удаления участника.
- **Границы данных.** Учёт квот и платежей ведём отдельно от добровольной аналитики взаимодействий. В события аналитики не включаем исходный код, пути файлов, промпты и секреты. До запуска утверждаем сроки хранения, доступ поддержки, экспорт и удаление данных. Кабинет обозначает неполноту метрик, если аналитика отключена или события ещё не поступили.


## Вход из настольной IDE

В macOS-сборке команда «Войти в TripleCode» открывает системный браузер.
После подтверждения email кнопка «Открыть TripleCode» возвращает в
приложение. Одноразовый код обменивается на отдельную сессию устройства
с привязкой PKCE S256 и проверкой `state`. IDE хранит сессию через
`SecretStorage`, обновляет токены при обращении к аккаунту и отзывает
сессию при выходе из IDE. Кабинет и сайт имеют собственную веб-сессию.

Клиентский контракт находится в `triplecode-web/packages/contracts/README.md`.
Синхронизация с IDE: [contracts-sync.md](contracts-sync.md). Сценарий входа: [scenarios/S09-login-pkce.md](scenarios/S09-login-pkce.md).
Механизм запуска AI и существующие политики пилота описаны отдельно выше.

## План и использование — направление (23.11.2026)

Ресерч Cursor и Devin показал две модели: у обоих сервер несёт стоимость
inference, поэтому квота меряется в токенах/ACU. У TripleCode BYOK —
пользователь платит провайдеру сам, сервер запросов не видит. Поэтому
идём по своему пути: сначала учёт и прозрачность, монетизация позже.

- **Usage events.** IDE репортит метаданные AI-запроса (функция, провайдер,
  модель, длительность, результат) на `/api/usage/event` под сессией
  устройства. Это trust-based канал — для аналитики и мягких квот,
  не для жёсткого биллинга.
- **Кабинет «Использование» / «План».** `/account/usage` и `/account/plan`
  (Pilot · BYOK): события по функциям/моделям, soft quota
  (`USAGE_SOFT_LIMIT`, default 500 / 30д). Превышение не блокирует IDE.
- **Квоты (жёсткие) / checkout.** Hosted checkout и платный биллинг — later;
  пилотный floor закрыт soft-счётчиками на аккаунт (щедрый лимит
  `USAGE_SOFT_LIMIT`).
