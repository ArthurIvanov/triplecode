# Продуктовый план TripleCode

## Для кого и зачем

Первый сегмент — разработчики небольших команд с существующим TypeScript/Node.js-репозиторием, привычками VS Code и регулярными AI-задачами на несколько файлов. Это рабочая гипотеза для пилота. Первый пользовательский сценарий: открыть свой проект, поручить небольшое изменение, проверить diff и результаты тестов, затем принять изменения или откатить их.

Основное позиционирование для проверки — **каждое изменение AI можно проверить до принятия**. В интерфейсе задачи рядом с diff видны файлы, переданные модели, исполненные команды и результаты проверок. Доступ к контексту и возможность отката входят в основной сценарий. Проверяем, сокращает ли это время ревью при сохранении качества, поскольку конкуренты уже предлагают diff, историю и настройки разрешений.

## Что проверяем у конкурентов

| Продукт | Сильная сторона | Что должен выдержать TripleCode |
| --- | --- | --- |
| VS Code | Экосистема, отладка, автоматизация, профили и несколько способов запуска агентов | Ежедневная работа с реальным проектом после импорта профиля |
| Cursor | Удобный переход от редактирования к плану, выполнению задачи и просмотру diff | Тот же класс задач с сопоставимым числом действий и предсказуемой клавиатурной навигацией |
| Devin | Долгие задачи в подготовленной среде, делегирование и передача результата на ревью | В полном релизе задачу можно продолжить после закрытия IDE и передать коллегам с историей проверок |

Сначала проводим 6–8 наблюдаемых миграций и интервью. Затем запускаем одинаковые задания в TripleCode и в привычной IDE участника, чередуя порядок. Фиксируем версию, модель, настройки, репозиторий и стартовый коммит. Для сравнения качества AI сохраняем набор задач с критериями и проверяем результат по ним. Отдельно сравниваем три гипотезы:

| Гипотеза | Как проверить |
| --- | --- |
| Предпросмотр импорта помогает перейти без потери рабочего окружения | Дать участнику его профиль, замерить время до запуска проекта и зафиксировать каждый ручной обход |
| Единая история контекста, изменений и проверок ускоряет ревью | Дать сопоставимые задачи и рандомизировать показ истории. Сравнить время и число пропущенных ошибок |
| Уход из локальной сессии в фоновую сокращает повторные объяснения | После MVP замерить число повторно переданных инструкций, частоту успешного продолжения и затраты на сессию |

## Карта паритета

Приоритеты описывают целевые обязательства TripleCode. Для каждой строки перед релизом QA фиксирует версию сравнения, ОС, сценарий и результат. Архитектурная база и ограничения распространения описаны в [исследовании](architecture.md).

| Область | Ориентир | Целевой этап | Критерий приёмки |
| --- | --- | --- | --- |
| Редактор, поиск, Explorer, палитра, разделение панелей | VS Code / Cursor | MVP | Открытие проекта, поиск, навигация, редактирование и восстановление окна клавиатурой |
| Терминал, Git, задачи, отладка и тесты | VS Code | MVP для Node.js, расширение матрицы в бете | Установка зависимостей, запуск тестов, breakpoint и просмотр Git diff на контрольном проекте |
| API расширений, языковые серверы и темы | VS Code | MVP для пилотного набора, бета для расширенной матрицы | Установка и фактическая активация на целевых ОС, отчёт по отсутствующим и несовместимым |
| Импорт из локальной установки и файла профиля | VS Code / Cursor | MVP | Предпросмотр, импорт, повтор, откат. Рабочие настройки, клавиши, сниппеты, темы, задачи и список расширений проверены на профиле пилота |
| Ask, план, многофайловый diff, подтверждение действий | Cursor / VS Code | MVP | Пользователь задаёт контекст, видит план, проверяет патч, принимает или отменяет изменение |
| AI-автодополнение в редакторе | Cursor Tab / Copilot | Бета | Подсказка у курсора для TypeScript/JavaScript. Проверены принятие, отмена, совместимость с IntelliSense и задержка при медленном провайдере |
| Прогноз следующей правки и переход к ней | Cursor Tab / Copilot NES | После базового автодополнения | Сначала правки в текущем файле, затем переходы и предложения в других файлах. Изменения можно просмотреть перед применением |
| AI-редактирование из выделения | Cursor / VS Code | Бета | По явной команде редактор показывает результат для выделенного фрагмента с возможностью отмены |
| Правила репозитория, дополнительные модели, MCP | Cursor / VS Code | Бета с поэтапным включением | Правила и ограничения доступа применяются ожидаемо. Подключения и разрешения видны пользователю |
| Синхронизация профилей, multi-root, notebooks, SSH, WSL, Dev Containers | VS Code | Проверка в бете, расширение до полного релиза | Публичная матрица реализаций и зависимостей. Для платформенных интеграций проверены поддержка и лицензирование |
| Фоновые задачи, облачные окружения, PR и передача сессии | Cursor / VS Code / Devin | Полный релиз | Сессия продолжается после закрытия IDE, результат доступен для ревью, повторная доставка сохраняет один итоговый PR |

Для закрытого MVP оцениваем успешность по участникам, завершившим первый запуск на своём репозитории. Для расширений считаем пройденные сценарии из зафиксированной матрицы, включая активацию и полезное действие. Показатели качества AI: доля задач, принятых после проверок, медиана времени ревью, доля откатов за 24 часа и стоимость принятых задач. Целевые значения для production устанавливаем по бете. Телеметрия собирает статусы и тайминги без содержимого репозиториев.

## Первая очередь работ

1. **IDE / архитектура.** Зафиксировать стабильный SHA Code — OSS, поднять чистую сборку, проверить базовые сценарии и записать исходные метрики запуска, памяти, поиска и задержки ввода под фоновой нагрузкой.
2. **Исследование / аналитика.** Собрать сценарии миграции и список расширений пилота. Для каждого расширения проверить источник, условия использования и активацию.
3. **Дизайн.** Спроектировать независимый визуальный стиль и прототип перехода от профиля к первому AI diff. Проверить клавиатурный сценарий, состояния ожидания, ошибки и возврат фокуса.
4. **IDE.** Реализовать прямой импорт из локальной установки VS Code, ручной импорт файла через Profiles, отчёт и безопасный повтор.
5. **AI / QA.** Провести сквозную сессию с одним провайдером и локальным контекстом, предложить патч, проверить принятие, отмену и восстановление после перезапуска.
6. **Продакт.** После прототипа провести пилот, обновить критерии MVP и принять решение о продолжении форка по данным сборки, расширений и стоимости обновлений.

Критический путь к MVP — сборка → совместимость расширений и импорт → AI diff → пилот на рабочих репозиториях. Дизайн и исследование можно вести параллельно со сборкой. Облачные задачи зависят от повторяемого локального runtime, оценки затрат и проверки изоляции.
