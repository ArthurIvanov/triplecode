# Правила работы с Figma MCP — Tripleform UI / Cursor

Документ описывает правила и рабочий процесс взаимодействия агента Cursor с Figma Model Context Protocol (MCP) сервером при разработке компонентов дизайн-системы Tripleform UI.

---

## 1. Общие сведения

- **Протокол:** Figma MCP обеспечивает программную связь между агентом и Figma API.
- **Цель:** разработка React-компонентов, точно соответствующих дизайну; автоматическая генерация и актуализация токенов; валидация реализации.
- **Файлы дизайна:** основной файл Tripleform UI содержит все компоненты, стили и переменные.
- **Переменные Figma (Variables):** используются как источники примитивных значений для токенов.
- **Доступ:** Figma MCP предоставляет **read-only** доступ. Запись в файлы дизайна через MCP невозможна и недопустима.

---

## 2. Архитектура токенов (критически важно)

Перед любой работой с Figma необходимо помнить: в Tripleform UI **двухуровневая** система токенов.

### Уровень 1 — Примитивные токены

Сырые значения без смысловой нагрузки: цвета (`--blue-500`), числа (`--4`, `--16`), типографика (`--fontSize-base`).

> **Никогда не используются напрямую в стилях компонентов.**

### Уровень 2 — Семантические функциональные токены

Отражают роль в интерфейсе, ссылаются на примитивы. Примеры: `--bg-accent-calm-enabled`, `--fg-main`, `--gap-related`, `--padding-m`.

> **Только они используются в стилях компонентов.**

Компонентного уровня токенов (вида `--button-primary-bg`) **не существует**. Компоненты напрямую используют подходящий семантический токен:

```css
background-color: var(--bg-lead-loud-enabled);
```

### Структура имени семантического токена

```
--{тип свойства}-{семантическая группа}-{визуальный акцент}-{состояние}
```

| Сегмент              | Допустимые значения                                                        |
| -------------------- | -------------------------------------------------------------------------- |
| Тип свойства         | `bg` (фон), `fr` (текст / заливка), `br` (граница)                         |
| Семантическая группа | `lead` (бренд), `accent`, `critical`, `success`, `warning`, `info`, `grey` |
| Визуальный акцент    | `calm` (спокойный), `loud` (заметный), `bold` (яркий)                      |
| Состояние            | `enabled`, `hover`, `active`, `disabled`                                   |

**Пример:** фон кнопки с критической ошибкой в обычном состоянии → `var(--bg-critical-bold-enabled)`.

## 3. Взаимодействие с Figma

### 3.1. Извлечение информации

При запросе данных о компоненте или узле:

- Всегда извлекай **Figma Variables**, привязанные к элементу, а не только вычисленные значения.
- Для каждого цвета, отступа и размера шрифта находи связанную переменную и её имя.
- Учитывай **Mode-переменные** (коллекции `Light` / `Dark`): MCP возвращает их отдельно. При извлечении цветов запрашивай значение для обоих режимов и убеждайся, что семантический токен корректно перекрывается в тёмной теме.
- Если в Figma использован цвет **без привязки к переменной** — фиксируй это как нарушение и предлагай заменить на подходящий токен.

### 3.1.1. Локальные свойства дизайна с префиксом `_`

- Все свойства Figma, имя которых начинается с `_`, локальны для дизайна. Они управляют отображением соответствующего свойства или слоя и **не переносятся в публичный React API**.
- Обычно свойства работают в паре: `_start` включает или выключает отображение слота в макете, а `start` задаёт его содержимое — иконку или другой компонент. Аналогично обрабатываются `_end` / `end` и другие пары.
- В коде слот принимает содержимое (`start?: ReactNode`, `end?: ReactNode`); его наличие определяет отображение. Не создавай отдельный boolean-переключатель из `_start` или `_end`.
- MCP может нормализовать имена и выдать такую пару как `start: boolean` и `start1: ReactNode`. Это артефакт генерации: сопоставляй свойства по роли и сохраняй имя содержимого `start`, а не `start1`. Не копируй сгенерированный API без проверки.
- Правило применяется ко всем компонентам. Префикс `_` сам по себе не означает состояние, токен или дополнительный публичный проп.

### 3.2. Сопоставление с токенами Tripleform UI

При переносе стилей из Figma в код:

1. Найди Figma Variable (например, `blue/500`).
2. Определи, какой примитивный токен ей соответствует (`--blue-500`).
3. Определи **семантическую роль** данного свойства в контексте компонента и состояния.
4. Найди подходящий семантический токен из `foundation.css` (например, `--bg-accent-calm-enabled`).
5. Используй в CSS **только** семантический токен: `var(--bg-accent-calm-enabled)`.

**Запрещается:**

- Использовать примитивные токены напрямую в стилях компонента.
- Создавать новые компонентные токены.
- Хардкодить значения из Figma (hex, px, rgba) без привязки к токену.

### 3.3. Приоритет при расхождениях

Если значение в Figma-макете незначительно отличается от существующего токена (например, `#4268e6` вместо `--blue-500: #4269e7`):

- **Используй существующий токен** — единичные отклонения в макете считаются погрешностью дизайна, а не намеренным изменением.
- Если отклонение существенное и явно намеренное — зафиксируй расхождение, сообщи о нём и **не вноси изменений в токены без дизайн-ревью**.

## 4. Рабочий процесс создания компонента по макету

### Обязательный порядок для каждой переданной Figma-ссылки

Каждая ссылка на разработку компонента запускает следующий процесс, включая повторную сверку после обновления макета:

1. **Проверить токены.** Сверить привязки Figma Variables и значения с токенами проекта: типографику (семейство, размер, вес, интерлиньяж, трекинг), цвета всех состояний, отступы, зазоры, размеры, скругления, границы, фокус и эффекты. Проверить доступные темы/режимы. Отдельно отметить отсутствующие привязки, недостающие токены и неподтверждённые значения.
2. **Проверить матрицу свойств.** Сопоставить свойства, типы, значения по умолчанию, слоты и состояния с матрицей Tripleform UI. Свойства с `_` оставить локальными для дизайна согласно разделу 3.1.1. Предложенные расширения API явно вынести на согласование.
3. **Сравнить с открытыми дизайн-системами.** Изучить актуальные официальные документацию и при необходимости исходники аналогичного компонента в Radix, Base UI, Atlassian, shadcn/ui, Chakra UI и MUI React. Сравнить API, семантику, доступность, клавиатуру, состояния, композицию и граничные сценарии. Если прямого аналога нет, указать это. Предложить применимые доработки с обоснованием и ссылками на источники; не копировать чужие возможности автоматически.
4. **Собрать предварительно для согласования.** Создать изолированный интерактивный предпросмотр вне проекта, по возможности переиспользуя существующие компоненты и токены. Проверить варианты, состояния и граничные сценарии. До явного разрешения пользователя не переносить компонент в проект и не менять ради него исходники, токены, экспорты или зависимости проекта. Разрешение на предварительную сборку либо на доработку предпросмотра не является разрешением на перенос.
5. **Сообщить о расхождениях.** Представить результат сверки, предлагаемый API, рекомендации других ДС и все найденные отличия между макетом, токенами проекта и предпросмотром. Для каждого отличия указать ожидаемое и фактическое поведение/значение, причину (если известна) и предлагаемое решение. Если данных недостаточно, явно обозначить непроверенные пункты; не заявлять полную синхронизацию без проверки.
6. **Применить после согласования.** Переносить в проект только после явной команды пользователя, например «добавляй в проект». Сохранять согласованный API и документировать оставшиеся согласованные отклонения. Затем выполнить проектные проверки, описанные ниже.

Следующие шаги описывают техническую детализацию этого процесса; генерация кода до согласования относится только к изолированному предпросмотру.

### Технические компоненты без макета Figma

Если пользователь явно поручил технический компонент без Figma (layout-примитив и аналоги), шаги сверки Variables/макета пропускаются, но **шаг изолированного предпросмотра остаётся обязательным**:

1. Согласовать API и матрицу / чек-лист.
2. Сравнить с открытыми ДС при необходимости.
3. Собрать изолированный интерактивный предпросмотр вне проекта (например `/tmp/tripleform-<name>-preview`), проверить ключевые сценарии, темы/RTL/адаптив где применимо; сохранить снимки и краткий журнал проверки.
4. Переносить в пакет только после явной команды («добавляй», «в проект»). «Делай» / «реализуй» без этой команды не означает перенос мимо предпросмотра.

### Шаг 1. Получить структуру узла

Запроси через MCP информацию о верхнеуровневом элементе и всех его детях.

### Шаг 2. Извлечь переменные

Для каждого стилистического свойства получи связанную Figma Variable. Обработай оба режима (Light / Dark).

### Шаг 3. Сопоставить с семантикой

Определи роль каждого стиля и найди соответствующий семантический токен из `foundation.css` (см. раздел 3.2).

### Шаг 4. Сгенерировать код

**React-компонент:**

- Используй семантический HTML-тег (`<button>`, `<input>`, `<a>` и т.д.).
- Добавь поддержку `forwardRef`.
- Пропсы строго соответствуют матрице Tripleform UI:
    - `appearance`, `variant`, `size` (якорь — `'base'`, не `'medium'`).
    - `loading` (спиннер), `skeleton` (заглушка при первичной загрузке) — разные состояния, не взаимозаменяемы.
    - `disabled`, `readOnly`, `required`, `selected`, `expanded`.
    - `open` / `defaultOpen` + `onOpen` / `onClose` для controlled / uncontrolled компонентов с видимостью.
    - `iconBefore` / `iconAfter` — принимают `string` (имя иконки из реестра) или `IconComponent`.
    - `elementLeft` / `elementRight` — универсальный слот `ReactNode | ReactNode[]`.
    - `color` для типографических компонентов (`'primary' | 'secondary' | 'muted' | 'disabled'`).
    - `count` для счётчиков в Badge, Tag, Chip, Tab.
    - `wrap` для ButtonGroup, Stack, Flex.
    - `gap`, `rowGap`, `columnGap` — только именованные значения, произвольный `string` запрещён.
- Базовая доступность:
    - `aria-busy="true"` при `loading`.
    - `aria-disabled="true"` при `disabled`.
    - `aria-label` обязателен для иконочных кнопок (без видимого текста).
    - `aria-describedby` связывает поле с `validationMessage` и `hint`.
    - `aria-labelledby` используется когда видимая метка существует отдельно от компонента.
    - `onKeyDown` / `onKeyUp` реализованы для всех интерактивных элементов.

**CSS-модуль:**

- Используй **только** семантические токены, никаких сырых значений из Figma.
- Скругления: `--base`, `--rounded`, `--micro` и т.д.
- Отступы: `--gap-*`, `--padding-*`; скругления: `--xs`…`--xl`, `--full`.

**Storybook:**

- Покрой все варианты `appearance`, `variant`, `size`.
- Покрой все состояния: `enabled`, `hover`, `focus`, `disabled`, `loading`, `skeleton`.
- Покрой controlled / uncontrolled паттерн для компонентов с `open` / `defaultOpen`.
- Добавь параметр `figma` со ссылкой на исходный узел Figma.

**Тесты:**

- `vitest-axe` для проверки доступности.
- Проверь корректность рендеринга всех вариантов.

### Шаг 5. Провести валидацию

После генерации сравни реализацию с Figma-спецификацией по следующим критериям:

| Что проверять                  | Ожидаемый результат                                                                 |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| Цвета фона, текста, границ     | Соответствующий семантический токен, а не hex                                       |
| Отступы (padding, gap, margin) | Семантический или размерный токен, а не px-значение                                 |
| Скругления                     | Алиас (`--base`, `--rounded` и т.д.)                                                |
| Типографика                    | `--fontSize-*`, `--fontWeight-*`, `--fontFamily-*`                                  |
| Цвет текста                    | Проп `color` (`'primary' \| 'secondary' \| 'muted' \| 'disabled'`), не `appearance` |
| Состояния                      | `loading`, `skeleton`, `disabled`, `open` покрыты и визуально совпадают с макетом   |
| gap / rowGap / columnGap       | Только именованные значения, не px-строки                                           |
| Тёмная тема                    | Mode-переменные корректно переключаются                                             |

Выведи список расхождений, если они есть. Расхождения, требующие дизайн-ревью, не исправляй самостоятельно.

## 5. Обновление и синхронизация токенов

Если необходимо обновить `foundation.css` из Figma:

1. Запроси все локальные переменные через MCP.
2. Для каждой переменной определи категорию: примитив или семантика.
3. Генерируй CSS-переменные **только для примитивного уровня** (новые цвета, размеры — если они действительно отсутствуют).
4. **Не создавай новые семантические токены автоматически.** Их добавление требует дизайн-ревью.
5. При конфликте между новым значением из Figma и существующим токеном — зафиксируй конфликт и запроси решение у команды. Самостоятельно не перезаписывай.
6. Убедись в корректности преобразования значений: `px` остаются `px`, `rgba` — в корректном синтаксисе CSS.

## 6. Типичные ошибки (anti-patterns)

| Ошибка                                             | Почему недопустимо                                                                  |
| -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `background: #4269e7`                              | Хардкод значения без токена — система теряет гибкость                               |
| `background: var(--blue-500)`                      | Прямое использование примитива в компоненте                                         |
| Создание `--button-primary-bg`                     | Компонентного уровня токенов в Tripleform UI не существует                             |
| Игнорирование Mode-переменных                      | Тёмная тема сломается или потребует ручных правок                                   |
| `tabIndex={1}` и выше                              | Нарушает порядок фокуса — запрещено правилами a11y                                  |
| Новые семантические токены без ревью               | Нарушает архитектурную целостность системы                                          |
| `gap="16px"` или `gap="1rem"`                      | Произвольный string в gap запрещён — только именованные значения из реестра токенов |
| `size="medium"`                                    | Значение `'medium'` удалено; якорное значение — `'base'`                            |
| `loading` вместо `skeleton` при первичной загрузке | Разные состояния: `loading` = процесс идёт, `skeleton` = данные ещё не получены     |
| `appearance` для цвета текстового компонента       | Для Text, Heading, Label, Caption используется `color`, а не `appearance`           |

## 7. Ограничения и безопасность

- Figma MCP предоставляет **read-only** доступ к файлам Tripleform UI.
- Не запрашивай данные из файлов, не относящихся к Tripleform UI, без явного указания.
- Токен доступа передаётся через переменные окружения — не раскрывай его в коде, логах или комментариях.
- При любом сомнении в корректности сопоставления токена — останавливайся и запрашивай подтверждение, а не делай предположение.

---

Следование этим правилам обеспечивает точное соответствие реализации дизайну, консистентность кодовой базы и архитектурную целостность дизайн-системы Tripleform UI.
